# 성능 측정 기록 (v1.0 → v1.1)

## 측정 조건

Render 무료 인스턴스 사양(메모리 512MB, CPU 0.1개)을 Linux cgroup으로 재현해 측정했다.

- 메모리 제한 512MB, CPU 할당 0.1개(`cpu.cfs_quota_us=10000 / period 100000`), 스왑 없음
- Python 3.11, torch 2.8.0, torchvision 0.23.0
- 테스트 이미지: 3024×4032 JPEG(약 6.6MB, 스마트폰 세로 사진 해상도), 800×1000 PNG
- 측정일: 2026-09-28

Render 실제 환경의 네트워크 지연과 컨테이너 기동 시간은 포함되지 않는다.
실제 배포 서버는 `scripts/bench.py --url https://waste-api-6xd9.onrender.com`으로 따로 측정한다.

## 결과

| 항목 | v1.0 (과제 제출본) | v1.1 |
|---|---|---|
| 서버 기동(모델 로드 포함) | 약 34~35초 | 약 34초 |
| 스마트폰 사진 1장 응답 | 3.2~4.6초 | 1.5~1.8초 |
| PNG(800×1000) 1장 응답 | 1.6~1.7초 | 0.7초 |
| 메모리 최대 사용량 (cgroup) | 505~512MB (제한에 도달, 회수 반복) | 404MB |
| 동시 5건 요청 | 1건 성공, 4건 연결 끊김, OOM kill 1회 | 5건 모두 성공 (각 약 9.5~10초) |
| 이미지가 아닌 파일(MIME만 image/jpeg) | 200 OK + category "Error" | 400 Bad Request |

## 원인과 조치

- **응답 시간·메모리:** v1.0은 4000px 원본을 전부 디코딩한 뒤 224px로 줄였다. v1.1은 JPEG 디코딩 단계에서 축소(`Image.draft`)하고 512px로 먼저 줄인 뒤 전처리한다. CPU 0.1개 환경에 맞춰 PyTorch 스레드를 1개로 고정했다.
- **동시 요청:** v1.0은 `async` 핸들러 안에서 추론을 직접 실행해 이벤트 루프가 막혔다. v1.1은 추론을 스레드풀에서 실행한다. CPU가 0.1개라 전체 처리량이 늘지는 않지만, 추론 중에도 `/health` 등 다른 요청이 응답하고 메모리 한도를 넘지 않는다.
- **서버 기동 시간:** 대부분 `import torch`와 모델 로드에 걸리는 시간이라 코드 수정으로는 거의 줄지 않는다. 슬립 방지(외부 모니터링 핑)로 대응한다.
